# AGENTS.md — repository map and how to verify each claim

Start with `README.md`. This file says where each part lives and which test or command checks it.

## Layout

| Path | What it is |
| --- | --- |

| `docs/sealed-signals/` | Specification and design: `MASTER_PROMPT.md` (the spec every lane built against, with its changelog), `contracts.md`, `trust-design.md`, `privacy-engineering.md`, `reach-design.md`, `question-contract.md`, `personas.md`, `judging-checklist.md`. |

| `docs/challenge/` | The organisers' original README and CLAUDE.md, unchanged, for reference. |
| `pitch/` | The six-slide deck (`sealed-signals-slides.html`, open in a browser) and its contact sheet. |
| `reports/` | `proof.json`, the transcript `make demo` writes. |
| `Makefile` | `make install`, `make check`, `make demo`, `make dev`, `make ui`. |

## How to verify each claim

| Claim | Command or file |
| --- | --- |
| The test suite passes | `make check`; committed output in `docs/evidence/make-check.txt` |
| The full loop runs offline from a clean clone in under 60 s | `make demo`; transcript in `docs/evidence/make-demo.txt` |
| The alert engine reproduces the April 2026 Chad move (TCD005, 6.1 → 6.9, the largest deterioration of 123) | `engine/tests/test_alerts.py`; `POST /api/alerts/replay` with `{"month_from":"Mar2026","month_to":"Apr2026"}`; fixture `fixtures/POST_alerts_replay_response.json` |
| Answers are committed before reveal and a link click never commits | `engine/tests/test_loop.py` (confirm step, correction before deadline, reveal refused before the deadline, n < 5 never revealed) |
| Masks are chosen per answer; the public ledger never returns an individual | `engine/tests/test_loop.py`; `scripts/validate_fixtures.py` fails on any aggregate with n < 5 |
| The draft checker rejects a number not in a record and holds unsourced claims | `engine/engine/draft.py`; `engine/tests/test_loop.py` |
| Hardening: encrypt/decrypt round trip, attestation fails on a flipped byte, blind token reuse rejected, anchor pending → anchored, registry reads logged | `engine/tests/hardening/` |
| Pattern reports never name a person; calibration items never appear on a pulse card | `engine/tests/hardening/test_patterns.py` |
| The country scan answers the brief's example question, hides ACAPS's view, shuffles per link, reveals at the deadline, keeps added risks out of the result | `engine/tests/test_scan.py` |
| Reach: one pulse per expert per seven days, STOP immediate and logged, no reminder carries a count, no message body or preview names a province or the ACAPS rating, an analyst cannot overwrite a preference the expert set | `engine/tests/reach/test_reach.py`, `test_reach_routes.py` |
| A typed reply counts where a link click does not; a second reply corrects; an unreadable reply reaches the analyst with its original text | `engine/tests/reach/test_inbound.py`; `POST /api/inbound/{channel}` |
| No message is actually sent | `GET /api/reach/status` (`does_not`), `GET /api/reach/outbox`, every delivery row's `transport: recorded`; `engine/tests/reach/test_reach_routes.py::test_every_channel_reports_that_nothing_was_sent` |
| Every API route has a true example payload | `fixtures/` and `scripts/validate_fixtures.py` |
| The UI builds | `make check`; the build output is in `docs/evidence/make-check.txt`. Screenshots of the three screens are added by the frontend lane at the freeze. |
| What is live and what is cached | `GET /api/radar/status` reports source and fetched_at per dataset; `data/acaps-api/README.md` |

## Feature flags

`FF_PQ`, `FF_BLIND`, `FF_ZK` (off), `FF_ANCHOR`, `FF_AGENTS` (off, model-optional), `FF_CALIBRATION` (off,
consent-gated), `FF_TEAMS` (off: needs an app registration in the agency's own tenant; falls back to email),
`FF_IVR` (off: needs a telephony account whose tariffs a local partner has to confirm; falls back to SMS),
`LLM_BASE_URL` and `LLM_API_KEY`, which come from the platform's shared AI gateway when `app.yaml`
declares `ai: true` -- no provider key is ever held in this repo. With them set, the expert card's
questions are written per risk and per expert by `engine/engine/question_gen.py`; without them that
generator is absent and the reviewed sets and the deterministic bank in `engine/engine/probes.py`
answer instead, so a card always has questions. Each flag is declared with its fallback in
`engine/engine/hardening/flags.py`. Every flag has a deterministic fallback so the demo never blocks;
the README and the UI state which path ran. Nothing in the pitch depends on a flag that is off.

## What is not built

Reach composes messages and records them; it sends nothing, because no provider account exists in this repository.
The Groth16 proof verifier behind `FF_ZK` is not implemented, so the group tree and the per-pulse nullifier are
enforced and the proof itself is not checked -- `GET /api/zk/status` says which. Both are described in
`docs/sealed-signals/privacy-engineering.md`, section 5.

## What is synthetic

Experts, their answers and the panel are synthetic and labelled as such in the UI and in `data/synthetic/`. ACAPS data
(export and API editions) is real and used under ACAPS's terms. `reports/proof.json` is the transcript of one offline run of the loop. The sensitivity test over the
104 resolved risks (MASTER_PROMPT section 7) is specified and not built, so no claim anywhere rests on it.
